# AGENTS.md — CloudKit storage plane

Operating guide for LLM agents working in this directory. Read `README.md` first for the architecture and `MIGRATION.md` for how albums move in and out of CloudKit; this file is the rules of the road. Design rationale and the chunked build plan live in `plans/cloudkit-migration/` (`00-overview.md`).

## What this directory is

The CloudKit cloud-storage backend (Option A: one `EncMedia` record per media item, carrying encrypted index fields + an eager thumbnail asset + a lazy blob asset, in the user's **private** database, plus one `EncAlbum` record per album). It is one of three storage planes; `.local` and (until removal) `.icloud` (iCloud Drive) live elsewhere.

## Non-negotiable invariants — do not break these

1. **Ciphertext only.** Nothing but the existing ENC2 encrypted files, the album-name ciphertext (`encName`) and the random `albumID` may reach CloudKit. Never upload plaintext, a plaintext album name, file path, or location. The crypto (`SecretFileHandlerV2`) is the privacy promise — CloudKit is transport only. If a change would put cleartext on a `CKRecord` or `CKAsset`, stop.
2. **`albumID` is a random UUID, minted once and stored.** It is minted when an album first becomes a CloudKit album (create, or migration planning when no existing album matches) and kept as the name of its `<albumID>/` marker directory (under `CloudKitAlbumMarker.rootDirectoryURL` in Application Support, never Caches) and in the migration plan; nothing derives it from the name. A CloudKit album's `Album.id` is `"<albumID>_cloudKit"`, so every `album.id`-keyed store survives a rename. Never fall back to a local `album.id` (`"<name>_local"` embeds the cleartext name), and never recompute an id from the name. The name is display data: `encName`, encrypted with the album key. The iCloud Drive flow keeps this rule as it is: `ICloudDriveAlbumMigration` adopts the `albumID` its folder's marker file names or resolves one through `resolveCloudKitAlbumID`, and the marker file only stores it; nothing derives an id from the folder or its name.
3. **Lazy blob.** `encBlob` must never appear in `desiredKeys` for metadata sync or gallery enumeration. It is fetched only by an explicit `fetchBlob`.
4. **Commit the change token only after the index is durably saved.** The store is *pure* — it does not persist the token on fetch. The coordinator advances it post-save. Don't move that ordering.
5. **Never delete a local original without a fresh verification** that the record is in CloudKit with the right size. See `MIGRATION.md`; this is the single rule the whole migration is built around. The same principle extends to references: **never drop a local reference or delete a parent record without a fresh `confirmAlbum`** — the strongly consistent gate that returns the record's current `albumID` via `fetchRecordMetadata`. Re-parents (`reassignAlbum`) use `confirmAlbum` before anything local changes, and a migration uses it to skip a record another album owns rather than save over it.
6. **Account-absent ⇒ local-only, never crash.** Anything other than `.available` means no-op gracefully. Mirror `CloudKitContainer`'s posture.
7. **`.local` and `.icloud` paths stay untouched** by changes in here.

## Architectural rules

- **Depend on the seam, not CloudKit.** All layers above the store talk to the `CloudKitMediaStoring` protocol (`CloudKitMediaStoring.swift`). Don't import or reference `CloudKit` types in the coordinator, file access, or app-level code — route new database operations through `CloudKitDatabaseAdapter` so they stay fakeable. Tests must never need the network or an iCloud account.
- **`reassignAlbum` re-parents records, metadata only.** `CloudKitMediaStoring.reassignAlbum(recordNames:toAlbumID:)` changes `albumID`, `albumRef` and `parent` via a batched fetch-then-save. It fetches with `desiredKeys: [albumID]` only — assets are never touched. Returns record names the server did not have (not an error). `confirmAlbum(recordName:)` is the strongly consistent gate before any local reference is dropped.
- **One coordinator walks the zone for every album.** `CloudKitSyncCoordinator.shared(albumManager:)` is the only coordinator outside a migration run; don't build one per album. It looks up each album's index and size sidecar by `albumID` through `AlbumManaging`, and every caller gets those stores from there too (`mediaIndexStore(for:)`, `sizeSidecar(for:)`) — never construct `MediaIndexStore(album:)` or `AlbumSizeSidecar(album:)` yourself, or two stores for one album race and drop writes.
- **A changed record that moved to another album is cleaned from the source index.** `CloudKitSyncCoordinator.performSync` checks the change feed's `changed` records: a record is upserted into the index of the album its `albumID` names, and removed from any other album's index that holds its `mediaID` (component evicted, cache cleared, size dropped, bus event emitted). This is how moves propagate to every device through the ordinary change feed — no tombstones needed.
- **The index records where each component lives.** `MediaIndexEntry` carries a `MediaComponentLocation` per component (`photoLocation`, `videoLocation`), so a Live Photo can have one half in CloudKit and the other on iCloud Drive. `MediaIndexCodec` keeps the `EIX1` magic and writes format version 2, with bits 2 and 3 of each entry's flags byte marking a component on iCloud Drive; a version-1 index still decodes, with every component at `.cloudKit`, and any other version is rejected. The index is a local cache of two sources, never a source of truth: sync rebuilds the CloudKit half and the folder scan the iCloud Drive half.
- **The coordinator owns only `.cloudKit` index components.** A component an index entry marks `.iCloudDrive` has no record yet and belongs to the iCloud Drive folder scan: the full-walk reap, feed deletes and the moved-record cleanup skip it (no index removal, preview delete, `markDeletedFromFeed` or bus event). A record arriving through the feed for such a component flips it to `.cloudKit` through the ordinary upsert, keeping the entry's date. A whole-zone rebuild after a lost index restores only the CloudKit half; the folder scan restores the rest.
- **`ICloudDriveFolderScanner` owns `.iCloudDrive` index components.** It scans the folder the album's local marker links to, only once that folder's own marker names the album. It adds a component for every media file the index has none for, dated with the `createdAt` the record will get (`MigrationItem.createdAt`, over the file metadata a migration reads), and removes one only when the file is gone in every form (`ICloudPlaceholderName.existsInAnyForm`) and `confirmAlbum` says no record exists; a check that cannot be made keeps the component. It never runs without iCloud Drive. Its watch rescans on every folder change and posts through `FileOperationBus`; `stopWatching()` is final.
- **Reads try four places, per component record name.** `CloudKitFileAccess.resolveComponent` serves `loadMedia`, `loadMediaToURLs` and the lightbox's metadata read from, in order: this device's copy of the record (blob cache or upload queue), the file in the album's linked iCloud Drive folder if already downloaded, a CloudKit fetch (or the ENC3 stream, which defers to a downloaded file), then an iCloud Drive download through `ICloudDriveMaterializing`. The folder is found through the local marker's link and read only once its own marker names the album (`ICloudDriveFolderScanner.verifiedFolder`). A component the index marks `.iCloudDrive` skips the fetch while its file is there: it has no record yet. The result's `CloudKitComponentReadSource` says which place served the read. Previews for `.iCloudDrive` components are made from their file, as an iCloud Drive album makes them.
- **Previews outlive the iCloud Drive file.** Previews stay in `DataStorageModel.thumbnailDirectory`, keyed by `mediaID`, whichever plane holds the bytes. Only a user delete removes one (`CloudKitSyncCoordinator.remove` or `removeICloudDriveComponent`, or the feed delete, reap or moved-record cleanup of a `.cloudKit` component). Nothing that deletes an iCloud Drive file because its bytes are in CloudKit (the migration's source delete in `LocalToCloudKitStep`, and any blob loop or parity sweep) may touch the preview, and neither may the folder scanner when it drops a component whose file is gone: the grid shows the thumbnail with no network after the file goes. `testPreviewSurvivesICloudDriveFileDeletion` and `testMigrationPreservesPreviewsInGlobalThumbnailDirectory` guard this.
- **One verified delete removes iCloud Drive files whose bytes are in CloudKit.** `ICloudDriveVerifiedDelete.delete(recordName:albumID:folder:)` takes one component and returns `deleted`, `skipped(reason)` or `failed(error)`. It deletes only when the folder's marker names the album, the file exists in some form, and a fresh `fetchRecordMetadata` finds the record in the album with the file's size. A downloaded file is sized from disk, an evicted one from file metadata; an unknown size keeps the file. The index is never consulted, an evicted file is removed as it is without a download, and it needs no key, so it runs while the phone is locked. An open viewer or player is not checked: it reads the file only while loading, and a load that loses the race fails and retries from the record. The record check is `CloudKitRecordPresence.check`, the same one `LocalToCloudKitStep` verifies with: a blob loop or parity sweep calls this operation and never repeats its checks.
- **A user delete of an item still on iCloud Drive removes its file, not a record.** `CloudKitFileAccess.delete(media:)` routes each component by its index location. A `.cloudKit` component's record goes through the delete queue (`CloudKitSyncCoordinator.remove`). A `.iCloudDrive` component has no record: its file is removed from the verified linked folder in every form, without a download, then `CloudKitSyncCoordinator.removeICloudDriveComponent` drops its index component, its size and, once no component of the media is left, its preview, and marks the record name deleted so a migration upload of it already in flight is deleted when it lands. A `.cloudKit` component's leftover file in the folder goes too, so no folder scan indexes the media again. The media leave the album's migration plan before any file goes (`MigrationPlanStore.remove(mediaIDs:)`), and every later save of that plan file in the process drops them, so a pass or album step holding an older copy cannot write them back. A delete that leaves the plan nothing to move runs `ICloudDriveAlbumFinish` unless a pass is running, which finishes the album itself. A delete with a component on iCloud Drive and no verified folder throws `ICloudDriveItemDeleteError.folderUnavailable` before deleting anything. Other devices see the file leave the folder, and their scan drops the component under its own rule; an evicted or not yet downloaded file is still there in some form and is kept.
- **Album-level writes on a partly migrated album touch the album, never the folder.** Rename, hide and cover change `album.json` and the `EncAlbum` record only (`updateCloudKitAlbumMarker`), while the blob migration runs; the linked folder keeps its name, so older builds show a stable folder, and its marker file names the album by id, so every device still finds it. New media goes to CloudKit through the upload queue and never into the folder. Only an item in CloudKit can be the cover: the lightbox disables "make cover" while the item is still on iCloud Drive.
- **An edit or move of an item still on iCloud Drive takes it out of the folder.** An edit's save (`CloudKitFileAccess.save` of media whose components the index places at `.iCloudDrive`) saves to CloudKit like any save, then retires the iCloud Drive copy: the media leaves the plan, its components move to `.cloudKit` in the index, their iCloud Drive sizes go and their files leave the verified linked folder. The record name is not claimed deleted and the preview stays. A move (`ICloudDriveItemMove`) downloads an evicted file, then into a CloudKit album uploads it straight into the target with `LocalToCloudKitStep`, as a move of a local item does, and into a local album copies the ciphertext; the item then leaves the source's plan, index, sizes and folder, without claiming its record name deleted and keeping its preview. A deferred item moves like any other; one whose record belongs to another album does not. Both hold the album's blob migration passes (`ICloudDriveBlobMigration.holdPasses`) while they write, so no pass uploads the old file over the edit or into the source album part-way through a move, and start one when done. An item that landed meanwhile is edited or moved as a CloudKit item. Only some components on iCloud Drive throws `ICloudDriveItemWriteError.partlyInCloudKit`, and an unverified folder `ICloudDriveItemDeleteError.folderUnavailable`, before anything is saved or moved.
- **Opening an item still on iCloud Drive prioritizes it as viewed.** The viewer and player load through `loadMediaForViewer` and `loadMediaToURLsForViewer`, which set `ViewerLoad.isActive` for every read the load makes; when `resolveComponent` serves such a load a component the index marks `.iCloudDrive` from the folder and the load then decrypts it, it records `.viewed` through `MigrationPlanStore.prioritizeViewed` and starts a pass for the album unless one is running, so the item reaches CloudKit now, under the pass's usual conditions. That also clears the item's deferral, since the decrypt disproves an unreadable file, a placeholder that never downloads and a missing key; `.recordInAnotherAlbum` stays. An open that does not decrypt, grid thumbnails, sharing, export and edits never prioritize. The viewer does not wait.
- **Deleting a CloudKit album removes its iCloud Drive half with it.** `AlbumManager.delete(album:)` does not count the album step or the blob migration as a move; it refuses only the moves `refusesDelete` names (every move but a paused whole-album move into the album from the folder it links, whose plan the delete removes). It throws `ICloudDriveItemDeleteError.folderUnavailable`, touching nothing, when the index has a component on iCloud Drive and the folder cannot be verified. Otherwise it records the album in `DeletedCloudKitAlbums` before removing anything, removes the local state, then `ICloudDriveAlbumDeletion.removeICloudDriveHalf` stops the pass (`ICloudDriveBlobMigration.stopPass` waits for the item in flight), stops the folder watch, removes the folder under a coordinated delete while its marker names the album, and removes the plan; only then is the record deleted, so the cascade and chunk reclaim cover an upload the last item landed. No save of the deleted album's plan file writes it again in the process. A folder whose marker names an album in `DeletedCloudKitAlbums` is not listed, adopted or migrated, and `runEveryFolder()` removes it, so neither a killed delete nor a remnant another device syncs back returns as an album. `applyRemoteAlbumDeletion` does the same on the other devices, without the record delete.
- **An iCloud Drive album gets its CloudKit album before any media moves.** `ICloudDriveAlbumMigration.run(folder:)` (or `run(album:)`) adopts the `albumID` the folder's marker file names, or else resolves one with `CloudKitMigrationManager.resolveCloudKitAlbumID` (the same resolution as a whole-album move, never a fork of it). It saves the `EncAlbum` only when the server lacks it, then writes the marker file, so a run that dies between the two finds the saved album by name next time. The record is saved without `migrationInProgress`. It then reads the marker again and, if it still names the album, writes the plan (`MigrationPlanStore(iCloudDriveMigrationFrom:cloudKitAlbumID:)`, kept under `CloudKitMigration/ICloudDriveAlbums/` so whole-album resume and `planRole` never see it). It writes no media record. It does nothing while locked, offline or without an account, and never mints an id over an evicted, conflicted or unreadable marker or re-saves an album whose record is gone. The walk that deletes an empty losing album also removes this device's plan into it. Every prepared run then brings the album and folder into parity.
- **The album list flips once, after the index is built.** A run adopts the CloudKit album with its folder link in the one `album.json` write the walk adopts with (`adoptCloudKitAlbum(record:key:linkingICloudDriveFolder:)`), only after the parity sweep has indexed the folder: the CloudKit album appears and the folder leaves the list together, never empty. Until then the run holds the album in `ICloudDriveAlbumFlipRegistry` and the walk and the reconciler do not adopt it; the parity sweep reaches the folder through the run, not the link. A marker that changed by flip time stops the run and removes the plan and index it wrote. A device already listing the album only gets its link written.
- **The album step runs for every folder at every launch, in the foreground only.** `CloudKitAlbumsSync` runs `ICloudDriveAlbumMigration.runEveryFolder()` after each sync pass's folder walk until one pass gets past its conditions in the process, and after every walk the marker monitor starts; it is never awaited by launch or shown as an overlay. A run does nothing without iCloud Drive (`MigrationDeviceConditions.hasICloudDrive`, checked before the container is read or the server reached), in the background (`AppRunState`, which covers a background task run), while locked, offline or signed out. A device without iCloud Drive sees only an album's CloudKit components: no folder walk, scan, sweep, delete or blob migration. Every `.prepared` run calls `startBlobMigration(albumID, folder)`, the one place an album's blob migration starts.
- **A user's start of an iCloud Drive album's move runs the album step.** `CloudKitMigrationManager.start(album:trigger: .user)` on an `.icloud` album runs `ICloudDriveAlbumMigration.run(album:)` and ends `.completed` with `destinationAlbum` set, or `.failed`; it never plans a whole-album move. The whole-album move stays reachable through `startWholeAlbumMove(album:trigger:)`, which an `.automaticResume`, `start(plan:)` of a written whole-album plan and `resume(album:)` use.
- **An index the sync did not create gets a whole-zone walk.** The coordinator walks the whole zone only for an album without an index, so a record another device uploaded before this device knew the album would be missed when the folder scan builds the index first. A run whose scan creates an album's index first records `CloudKitZoneWalkRequests.request(albumID)`; the coordinator treats a requested album as one without an index, and clears the request once a whole-zone walk has applied to it.
- **A linked iCloud Drive folder is the album's source, never drained.** `DataStorageModel.hasMigratedToCloudKit` (no re-creating the folder) holds for a folder a CloudKit album's `album.json` links (`isLinkedICloudDriveFolder`) and for the drained source of a finished whole-album move (`isDrainedICloudDriveSource`: a CloudKit album with the folder's name and key that does not link it). The album list hides a linked folder by its marker, or by the link while the marker is evicted or in conflict with a version naming the album.
- **The parity sweep chooses components; the verified delete decides.** `ICloudDriveParitySweep.run(albumID:folder:)` runs the folder scan, then passes every component the index places at `.cloudKit` whose file is still in the folder (in either form) to `ICloudDriveComponentDeleting` (`ICloudDriveVerifiedDelete`), and nothing else: no `.iCloudDrive` component, no file the index lacks. It adds no checks of its own and does not touch the index, sizes or previews. `ICloudDriveAlbumMigration` runs it for every folder on every run, marker or not, so files older builds added get indexed and files whose upload landed (a blob loop killed before its delete, a failed delete, another device's upload) go on the next run. A run in parity scans nothing new and passes nothing.
- **One ordering function decides what migrates next.** `BlobMigrationOrder.next(items:deviceState:seed:)` is pure over each plan item's stored `kind`, `priorityRequest`, `deferralReason`, `createdAt` and state, plus `BlobMigrationDeviceState` and this device's seed. The seed (`BlobMigrationOrder.seed(deviceID:mediaID:)`, the first 8 bytes of a SHA-256, big-endian) is the primary order of the encrypting, ciphertext-only and deferred tiers, so devices working through one album start on different items; requested and viewed items never use it. It stands in for a lease, which there is none of: don't replace it with `Hasher`, which is seeded per process. A user request is recorded only through `MigrationPlanStore.prioritize(_:reason:)` (`prioritizeViewed(_:at:)` for a viewer open that decrypted the item), and a `.viewed` request also clears the deferrals the decrypt disproves (or the matching `MigrationPlan` methods on a plan held in memory, which the holder then checkpoints); nothing else reorders items. Every later save of that plan file in the process stamps the request again, and clears those deferrals again, so a pass or album step holding an older copy cannot drop it. Locking only changes eligibility: no `.encrypting` item is returned while locked, whatever its request. A new reason is a new `MigrationPriorityReason` case and tier.
- **Thumbnail repair follows the record, not the read.** Every open (`loadMedia`, `loadMediaToURLs`) runs `repairThumbnailIfMissing`, whether a CloudKit fetch, the blob cache or the iCloud Drive file served the bytes, so an item that reached CloudKit without `encThumbnail` gets one from whichever read opens it. A component the index marks `.iCloudDrive` has no record and is never sent to CloudKit; its open only writes the local preview.
- **Names live in `CloudKitSchema.swift` only.** Never hardcode a record type, field, zone, or container id elsewhere. A rename happens in one place — and remember a new record type or field needs a Production schema deploy before a release build can write it (`Documentation/cloudkit-schema-deploy.md`).
- **Concurrency matches the codebase:** `actor` for storage/sync state (`CloudKitSyncCoordinator`, `CloudKitBlobCache`, `CloudKitFileAccess`), `@MainActor` for view models and the migration engine. The store uses `NSLock` for its defaults maps.
- **Reuse, don't reinvent:** crypto (`SecretFileHandlerV2` for metadata-bearing writes; **reads must use the format-agnostic `SecretFileHandler`** — V2 throws on V1-format blobs and legacy libraries are full of them, see ENC-135 and the `CloudKitFileAccess.swift` header), previews (`DiskFileAccess.createPreview`), the local index (`MediaIndexStore`), deterministic hashing (`SyncedStoreEncryptionHandler`), the gallery event bus (`FileOperationBus`). Extend these, don't fork them.
- **Two CloudKit records per Live Photo, one index entry.** Record names are `mediaID#<mediaTypeRawValue>` (see `CloudKitFileAccess.componentRecordName`); the `mediaID` groups them. Keep per-blob tracking and cache keys keyed by **record name**, not `mediaID`, or the two components collide.
- **The album record comes first.** `EncMedia` references its `EncAlbum` parent, and CloudKit rejects a save whose parent isn't on the server. Anything that creates media must ensure the album record exists (`saveAlbum` is idempotent) rather than assuming the reconciler already pushed it.
- **The store creates the zone, on writes only.** `CloudKitMediaStore.withZone` runs every record write (`upload`, `saveAlbum`, `reassignAlbum`, `attachThumbnail`): it creates `EncameraZone` first (no round trip once the container's flag is set), and a write that finds the zone gone creates it again and retries once. Callers never ensure or recreate the zone, and `CloudKitMediaStoring` has no method for it. Reads, deletes and the subscription never create the zone: a missing zone holds nothing, and the erase (`DestructiveOnboardingCoordinator.zoneConfirmedEmpty`) and `ExistingDataProbe` read the zone to learn whether it exists, so a read that created it would undo an erase and mark a device that never used CloudKit as having provisioned it. A caller that must write after a read reads `zoneNotFound` as nothing there: `ICloudDriveAlbumMigration` takes it from `fetchAlbum` as no album yet, so its `saveAlbum` creates the zone.

## Rules specific to the migration engine

Read `MIGRATION.md` before touching `CloudKitMigrationManager.swift`, `CloudKitMigrationPlan.swift`, `MigrationItemStep.swift`, or the launcher/resumer/registry in `Encamera/AlbumManagement/`. `CloudKitMigrationManager` is the one engine for every transfer between local storage and CloudKit: a `MigrationPlan` carries a source and destination endpoint and a scope (`.album` or `.items`), and the direction follows from the storage pair. Per-item work lives in `LocalToCloudKitStep` and `CloudKitToLocalStep`. See the "Media moves" and "Renaming a CloudKit album" sections in `MIGRATION.md` for the full story. The short version:

- **Checkpoint after every state transition, not periodically.** One transition per write is what makes resume exact.
- **One run per album per process.** The engine's static active set is claimed atomically on the main actor. Don't add an `await` between the check and the claim, and don't let a second surface drive the same plan.
- **Cancel rolls back, pause resumes.** A whole-album cancel rolls the move back and deletes the plan (`rollBack(plan:)`); an item move's cancel, or a rollback that cannot finish, stamps `cancelledAt` so background auto-resume skips the plan. A pause leaves it freely resumable. Don't collapse the two. An iCloud Drive album's move into the CloudKit album that links its folder has no cancel at all, since there is nothing to roll back to: the engine refuses it, and the blob migration only pauses (`PauseReason`). An item it can't move right now is deferred: it stays `pending` with a `deferralReason`, stays readable from the folder, and is retried last, on Wi-Fi only (`BlobMigrationOrder`).
- **Terminal states belong to `run()`.** Publishing `.completed` or `.failed` from planning tears the UI binding down before the work happens.
- **Publish progress through `publishProgress`/`setPhase` only.** A direct assignment silently drops the phase, and a phase that isn't published is invisible to the UI.
- **A surviving plan file always means unfinished business** — including one with no per-item work left, which means finalize failed and must be retried.
- **An `.icloud` source is materialized batch by batch before upload.** Evicted files enumerate as placeholders the engine would otherwise terminally skip; a file still a placeholder fails rather than skips.
- **A whole-album move runs two passes, in both directions.** No source copy is deleted until every item has verified at the destination, and a cancel is ignored once the deletes start. Don't collapse it to per-item removal: a stopped move must leave its source whole, and a move back's local album is invisible here until finalize. A move back's item is `sourceDeleted` only once its record delete is confirmed; a queued one stays `removalPending` and blocks finalize. This rule stays in force for both whole-album moves, local to CloudKit included.
- **The iCloud Drive flow deletes per item, and must not be made two-pass.** `ICloudDriveBlobMigration` deletes each file through the verified delete (`ICloudDriveVerifiedDelete`) right after its item verifies. iCloud Drive and the CloudKit private database draw on the same iCloud quota, so holding both copies for a move that runs for days doubles the album's footprint and makes `quotaExceeded` likely for the largest libraries. The two-pass rule keeps a stopped move's source album whole and visible; here there is no separate source album, only one album whose items are in one of two places.
- **Locked work is ciphertext only.** The blob migration takes keys from `BlobMigrationKeyCache`, filled only while the phone is unlocked and never from the keychain while it is locked (the keychain items stay `kSecAttrAccessibleWhenUnlocked`). A slice that starts locked with no keys held exits at once without reading a plan or the keychain. While locked only `.ciphertextOnly` items move; an `.encrypting` item (a video at or over `SeekableEncryptedFormat.threshold`, re-encrypted before upload) starts only with protected data available, and one under way when the phone locks is abandoned at its next chunk, its plaintext scratch removed and the item put back to `pending`. No plaintext is ever written while locked.

## Build & test

The project is generated by **XcodeGen** from `project.yml`; this code lives in the `EncameraCore` SPM package. There is no `EncameraTests` *scheme* — `EncameraTests` and `EncameraCoreTests` are test targets on the `Encamera` scheme.

```bash
# After adding files / editing project.yml or *.entitlements:
xcodegen generate

# EncameraCore tests, natively on the Mac (the default for changes in this package)
cd EncameraCore && CFFIXED_USER_HOME="$(mktemp -d)" swift test --filter 'EncameraCoreTests.CloudKit'

# Unit tests (both unit targets)
xcodebuild test -scheme Encamera -destination 'platform=iOS Simulator,name=iPhone 16'

# EncameraCore tests, app-hosted on the simulator
xcodebuild test -scheme Encamera -only-testing:EncameraCoreTests \
  -destination 'platform=iOS Simulator,name=iPhone 16'

# UI tests (CloudKit UI tests run offline via -CloudKitMockMode)
xcodebuild test -scheme EncameraUITests -destination 'platform=iOS Simulator,name=iPhone 16'
```

Always re-run `xcodegen generate` after touching `project.yml` or any `*.entitlements`, or the change won't reach the project. The `EncameraDeviceSmoke` scheme and its environment variables are defined in `project.yml` — regenerate and diff rather than restoring a scheme file by hand.

## Testing rules

- Add unit tests at the `CloudKitMediaStoring` / `CloudKitDatabaseAdapter` seam with a fake — never hit a live container in automated tests.
- For UI-visible behavior, drive `InMemoryCloudKitMediaStore` via the `-CloudKitMockMode` launch arg (wired through `UITestSupport` / `CloudKitStoreProvider.makeStore`). `-CloudKitUploadDelayMs=N` and `-CloudKitDownloadDelayMs=N` slow a migration enough for the overlay to be observed.
- The device suites in `UITests/` (`CloudKitDeviceSuiteTests`, the migration progress/durability suites, `TwoDeviceCloudKitMigrationDeviceTests`, `CloudKitMigrationProductionWallDeviceTests`) hard-gate on environment variables set by the `EncameraDeviceSmoke` scheme and `Scripts/*.sh`, so they skip themselves everywhere else. Keep that gating when adding one.
- `CloudKitFlightCheck` is the only live-container path inside the app and is **manual** (a human runs it on a signed device from the debug workbench). Don't try to run it in CI; if you change a real code path it exercises, update the relevant step.

## Gotchas worth knowing before you edit

- **CloudKit owns the asset temp URL** and may delete it — copy the file out before the fetch returns (`CloudKitMediaStore.fetchAsset`).
- **The deleted-records list spans the whole shared zone** and carries no `albumID` — filter to records this album actually holds before acting.
- **A wiped index with a surviving change token** would skip every historical record forever — the coordinator detects a CloudKit album without an index and walks the whole zone. Don't remove that guard. A full walk leaves an empty album an empty index, so the guard does not fire again on every sync.
- **The zone-created flag is keyed by container id** — a container change (Debug vs Release, or a re-point) must recreate the zone. The flight check verifies the zone on the *server* rather than trusting the flag.
- **Missing thumbnail is allowed** (preview generation can fail); uploading a nil asset would fail the whole record, so the eager thumbnail is simply omitted.
- **Per-record errors arrive wrapped in `.partial`.** A single-record save that failed on quota or a missing account reports it as a partial failure, so a `switch` on the raw error never matches. Switch on `mapCKError(error)`, which collapses them (`CloudKitMediaStoreError.unwrappingPartial`).
- **`invalidArguments` on a save usually means an undeployed Production schema**, not a bad argument. That is a distinct, non-recoverable failure the user needs told about — don't fold it into a generic error.
- **`album.json` is the local truth for a CloudKit album's name, hidden flag and cover.** A local change writes the marker with `dirty = true` and saves the record in the background; the reconciler pushes every dirty marker and rewrites clean ones from the change feed. Write through `AlbumManager.updateCloudKitAlbumMarker`, not the marker file directly, or the change never reaches the record. CloudKit albums keep nothing in the name-keyed `AlbumsSyncedStore`; a move between storages carries the hidden flag and cover across.
- **Long-lived `CKOperation`s are gone (ENC-133)** and must not come back: re-enqueueing one raises an uncatchable `NSException` on the next launch. Background progress rests on the checkpoint plus a `BGProcessingTask`.
- **Use `CloudKitBlobCache.shared`.** A second instance writes the on-disk cache index from a divergent snapshot and orphans the other's blobs.

## When in doubt

Trust the code over the plan docs (they were written from a snapshot and can drift). If reality diverges from `plans/cloudkit-migration/`, follow the code and note the divergence. If a change touches the privacy invariants above, prefer to surface the concern rather than proceed.
